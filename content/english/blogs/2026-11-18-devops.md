Kubernetes is finally pulling the plug on the kube-proxy IPVS backend, and the migration window is tight. If you're still running IPVS in production, you have until Kubernetes 1.40 to move, and the nftables backend is where you're headed.

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/lIh0cw89PalfPIicq4yHbg/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfGt1YmUtcHJveHktaXB2cy1pcy1kZWFkLXBsYW4teW91ci1taWdyYXRpb24tbm93fHxodHRwczovL2t1YmVybmV0ZXMuaW8vYmxvZy8yMDI2LzExLzE2L2lwdnMtcmVtb3ZhbC8_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t" target="_blank" rel="noopener noreferrer">Source: kubernetes.io ↗</a></p>

Kubernetes SIG Network has officially [deprecated the kube-proxy IPVS backend](https://ecommerce-api.datafortress.cloud/r/brieftechnews/lIh0cw89PalfPIicq4yHbg/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfGt1YmUtcHJveHktaXB2cy1pcy1kZWFkLXBsYW4teW91ci1taWdyYXRpb24tbm93fHxodHRwczovL2t1YmVybmV0ZXMuaW8vYmxvZy8yMDI2LzExLzE2L2lwdnMtcmVtb3ZhbC8_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t) as of Kubernetes 1.35, with removal scheduled for 1.40. That gives you roughly four minor releases to move off it.

IPVS was introduced to fix the latency problems in the iptables backend, both in the data plane and the control plane. The problem: the kernel IPVS API never fully mapped onto the Kubernetes Services API. The mismatch created edge cases that SIG Network had to carry forever, and the maintenance cost stopped being worth it.

Your options are the nftables backend, which has been GA since 1.33, or the iptables backend. If you've been avoiding nftables because it was new, that excuse expired a few releases ago. The deprecation notice is the push you need to test your Services against nftables now, not when 1.40 lands and your cluster refuses to start.

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/y0cXyezdZNPFp0uWRHcOvQ/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfGNsb3VkZmxhcmVzLWtpdGVzdXJmLWEtYnJvd3Nlci1lbmdpbmUtd2l0aC1uby1icm93c2VyfHxodHRwczovL2Jsb2cuY2xvdWRmbGFyZS5jb20va2l0ZXN1cmYtb3Blbi1zb3VyY2UvP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ" target="_blank" rel="noopener noreferrer">Source: blog.cloudflare.com ↗</a></p>

Cloudflare has [open-sourced Kitesurf](https://ecommerce-api.datafortress.cloud/r/brieftechnews/y0cXyezdZNPFp0uWRHcOvQ/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfGNsb3VkZmxhcmVzLWtpdGVzdXJmLWEtYnJvd3Nlci1lbmdpbmUtd2l0aC1uby1icm93c2VyfHxodHRwczovL2Jsb2cuY2xvdWRmbGFyZS5jb20va2l0ZXN1cmYtb3Blbi1zb3VyY2UvP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ) under Apache 2.0, and it's a genuinely different take on headless browsing. It parses HTML, applies CSS, executes JavaScript, and renders screenshots entirely on Cloudflare Workers, with no browser container anywhere in the path.

The trick is compiling Rust to WebAssembly. Kitesurf leans on open-source Rust crates like Blitz, Stylo, Boa, and Linebender, all compiled to WASM and running on Workers' compute. It supports the Chrome DevTools Protocol, so existing Puppeteer clients can talk to it without rewriting their tooling.

For anyone running AI agents that need to interact with web pages, this removes a whole class of infrastructure. No more browser containers to patch, scale, or watch for memory leaks. Deploy it to Workers or run it locally from the GitHub repo. The trade-off is performance and full browser fidelity, but for agent workloads that just need to load a page, click a button, and take a screenshot, this could be enough.

Xin Yao's talk at [GOTO Copenhagen](https://ecommerce-api.datafortress.cloud/r/brieftechnews/NPHVP7EuXpUyIpilnPuWzg/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfHRlY2huaWNhbC1kZWJ0LWlzLXRoZS1wcmljZS1vZi1sZWFybmluZy1ub3QtYS1zaW58fGh0dHBzOi8vd3d3LmluZm9xLmNvbS9uZXdzLzIwMjYvMTEvdGVjaC1kZWJ0LWxlYXJuaW5nLWRvaW5nLz91dG1fc291cmNlPWJyaWVmLXRlY2gtbmV3cy5jb20) reframes technical debt as something other than a failure. His argument: debt is what you accumulate when you design software with incomplete knowledge. It's the price of learning by doing, not a mark of poor engineering.

The problem starts when software doesn't catch up with what you've learned. Debt becomes pathological when it's permanent, when the codebase never absorbs the lessons that created the debt in the first place. Yao also notes debt can be a deliberate business strategy, a way to communicate with management about what's being deferred and why.

The real tension is optionality. Every feature you ship removes some future options, and the challenge is balancing feature delivery against preserving room to maneuver. For engineers who've been told debt is always bad, this is a useful counterweight. For managers, it's a reminder that the fix isn't just more refactoring, it's building shared understanding faster.

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/o6OWaWX3xMjLLZUXMDsItQ/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfHNhbGVzZm9yY2VzLTUtbWlsbGlvbi1hdXRvc2NhbGluZy1wbGF5Ym9va3x8aHR0cHM6Ly9hd3MuYW1hem9uLmNvbS9ibG9ncy9jb250YWluZXJzL2hvdy1zYWxlc2ZvcmNlLWVmZmljaWVudGx5LXJpZ2h0LXNpemVzLWt1YmVybmV0ZXMtd29ya2xvYWRzLWF0LXNjYWxlLW9uLWFtYXpvbi1la3MvP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ" target="_blank" rel="noopener noreferrer">Source: aws.amazon.com ↗</a></p>

Salesforce published a detailed breakdown of how it [right-sizes Kubernetes workloads at scale on EKS](https://ecommerce-api.datafortress.cloud/r/brieftechnews/o6OWaWX3xMjLLZUXMDsItQ/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfHNhbGVzZm9yY2VzLTUtbWlsbGlvbi1hdXRvc2NhbGluZy1wbGF5Ym9va3x8aHR0cHM6Ly9hd3MuYW1hem9uLmNvbS9ibG9ncy9jb250YWluZXJzL2hvdy1zYWxlc2ZvcmNlLWVmZmljaWVudGx5LXJpZ2h0LXNpemVzLWt1YmVybmV0ZXMtd29ya2xvYWRzLWF0LXNjYWxlLW9uLWFtYXpvbi1la3MvP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ), and the numbers are worth your time. The fleet: over 1,400 EKS clusters, individual clusters up to 2,500 nodes, roughly 1,000 workloads. The result: more than $5 million in cumulative infrastructure savings.

The approach is a multi-dimensional scaling strategy that pairs Vertical Pod Autoscaler with Horizontal Pod Autoscaler. The key insight is keeping the two controllers from reacting to the same signal. For Istio workloads, VPA adjusts CPU and memory while HPA scales replicas based on proxy connection count. Different signals, complementary actions.

The backstory matters. Salesforce's static resource management caused production incidents, high operational toil, and scalability bottlenecks. The fix wasn't a single tool, it was a coordinated strategy across the whole fleet. If you're running EKS at any scale, this is a concrete reference architecture for how to make VPA and HPA work together instead of fighting each other.

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/8vdCg1B2XF95XRygkW98ww/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfHlvdXItb3BlbnRlbGVtZXRyeS1waXBlbGluZS1pcy1lYXRpbmcteW91ci1jcHV8fGh0dHBzOi8vd3d3LmNuY2YuaW8vYmxvZy8yMDI2LzExLzE3L2lzLXlvdXItb3BlbnRlbGVtZXRyeS1waXBlbGluZS1iZWNvbWluZy1hLXBlcmZvcm1hbmNlLWJvdHRsZW5lY2svP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ" target="_blank" rel="noopener noreferrer">Source: cncf.io ↗</a></p>

A presentation at [Cloud Native Days Austria 2026](https://ecommerce-api.datafortress.cloud/r/brieftechnews/8vdCg1B2XF95XRygkW98ww/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfHlvdXItb3BlbnRlbGVtZXRyeS1waXBlbGluZS1pcy1lYXRpbmcteW91ci1jcHV8fGh0dHBzOi8vd3d3LmNuY2YuaW8vYmxvZy8yMDI2LzExLzE3L2lzLXlvdXItb3BlbnRlbGVtZXRyeS1waXBlbGluZS1iZWNvbWluZy1hLXBlcmZvcm1hbmNlLWJvdHRsZW5lY2svP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ) makes the case that observability has a cost, and it's higher than you think. OpenTelemetry pipelines consume significant CPU, memory, network, and storage as applications scale, and the overhead comes from the entire pipeline: span generation, collection, processing, exporting, and storage.

The uncomfortable finding is that a single overhead percentage is misleading. The cost is workload-dependent, so your neighbor's 5% overhead tells you nothing about your own. The investigation used Telemetrygen to identify five common Collector configuration problems, including excessive attributes, unbounded queues, and expensive processing.

The practical takeaways: memory-limiter placement matters, sampling is a trade-off you have to make consciously, and tail sampling requires trace-aware routing when Collectors scale horizontally. If your observability stack is slowing down your applications, the fix is probably in your Collector configuration, not in buying more nodes.

<h2 id="platform-teams-obstacles-vs-challenges"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/cXRll7yjJutuRTEMgzoc4g/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfHBsYXRmb3JtLXRlYW1zLW9ic3RhY2xlcy12cy1jaGFsbGVuZ2VzfHxodHRwczovL29jdG9wdXMuY29tL2Jsb2cvcGxhdGZvcm0tY2hhbGxlbmdlLWlzLXRoZS13YXk_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t" target="_blank" rel="noopener noreferrer">Platform teams: obstacles vs. challenges</a></h2>

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/cXRll7yjJutuRTEMgzoc4g/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfHBsYXRmb3JtLXRlYW1zLW9ic3RhY2xlcy12cy1jaGFsbGVuZ2VzfHxodHRwczovL29jdG9wdXMuY29tL2Jsb2cvcGxhdGZvcm0tY2hhbGxlbmdlLWlzLXRoZS13YXk_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t" target="_blank" rel="noopener noreferrer">Source: octopus.com ↗</a></p>

Octopus Deploy's Steve Fenton uses [Future of Platform Engineering survey data](https://ecommerce-api.datafortress.cloud/r/brieftechnews/cXRll7yjJutuRTEMgzoc4g/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfHBsYXRmb3JtLXRlYW1zLW9ic3RhY2xlcy12cy1jaGFsbGVuZ2VzfHxodHRwczovL29jdG9wdXMuY29tL2Jsb2cvcGxhdGZvcm0tY2hhbGxlbmdlLWlzLXRoZS13YXk_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t) to draw a useful distinction. Obstacles are things that prevent platform success: lack of clear strategy, budget, and skills. Challenges are things like tooling sprawl, competing priorities, resistance to change, and technical complexity.

The finding that matters: high-performing platforms are more likely to face challenges than obstacles. Tooling sprawl is the top challenge for successful teams, not a sign of failure. The top obstacle is lack of clear strategy, which leads to frustration and teams building from scratch instead of using best-in-class tools. If your platform team is struggling, first ask whether you have a strategy problem or a challenge problem. The fixes are completely different.

<h2 id="ubers-secure-ai-framework-for-autonomous-agents"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/ia9qzg7x8WY-7EDjNhtEZg/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfHViZXJzLXNlY3VyZS1haS1mcmFtZXdvcmstZm9yLWF1dG9ub21vdXMtYWdlbnRzfHxodHRwczovL3d3dy5pbmZvcS5jb20vbmV3cy8yMDI2LzExL3ViZXItc2VjdXJlLWFpLWZyYW1ld29yay8_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t" target="_blank" rel="noopener noreferrer">Uber&#x27;s Secure AI Framework for autonomous agents</a></h2>

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/ia9qzg7x8WY-7EDjNhtEZg/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfHViZXJzLXNlY3VyZS1haS1mcmFtZXdvcmstZm9yLWF1dG9ub21vdXMtYWdlbnRzfHxodHRwczovL3d3dy5pbmZvcS5jb20vbmV3cy8yMDI2LzExL3ViZXItc2VjdXJlLWFpLWZyYW1ld29yay8_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t" target="_blank" rel="noopener noreferrer">Source: infoq.com ↗</a></p>

Uber developed a [Secure AI Framework](https://ecommerce-api.datafortress.cloud/r/brieftechnews/ia9qzg7x8WY-7EDjNhtEZg/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfHViZXJzLXNlY3VyZS1haS1mcmFtZXdvcmstZm9yLWF1dG9ub21vdXMtYWdlbnRzfHxodHRwczovL3d3dy5pbmZvcS5jb20vbmV3cy8yMDI2LzExL3ViZXItc2VjdXJlLWFpLWZyYW1ld29yay8_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t) to govern autonomous AI agents across their lifecycle, addressing prompt injection, tool poisoning, goal hijacking, and hallucination-driven actions. The framework has three layers: provisioning-time registration in the Uber AI Registry with automated analysis via Argus, runtime behavioral authorization through AI Registry, AI Guards, and Agent Guard runtime hooks, and post-deployment Continuous Assurance with unified execution traces and replay.

The notable design choice: per-agent intents worked better than generic thresholds. The framework extends traditional identity and API controls to evaluate whether an agent's action fits the user's request, purpose, permissions, and context. For anyone deploying autonomous agents, this is a reference architecture for what governance looks like when agents act on their own.

<h2 id="canonicals-edge-archive-ai-written-security-patches"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/7_wml3XBO_0HOLZj_BBQDQ/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfGNhbm9uaWNhbHMtZWRnZS1hcmNoaXZlLWFpLXdyaXR0ZW4tc2VjdXJpdHktcGF0Y2hlc3x8aHR0cHM6Ly93d3cub21ndWJ1bnR1LmNvLnVrLzIwMjYvMTEvdWJ1bnR1LXByby1haS1zZWN1cml0eS1hcmNoaXZlP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ" target="_blank" rel="noopener noreferrer">Canonical&#x27;s Edge archive: AI-written security patches</a></h2>

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/7_wml3XBO_0HOLZj_BBQDQ/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfGNhbm9uaWNhbHMtZWRnZS1hcmNoaXZlLWFpLXdyaXR0ZW4tc2VjdXJpdHktcGF0Y2hlc3x8aHR0cHM6Ly93d3cub21ndWJ1bnR1LmNvLnVrLzIwMjYvMTEvdWJ1bnR1LXByby1haS1zZWN1cml0eS1hcmNoaXZlP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ" target="_blank" rel="noopener noreferrer">Source: omgubuntu.co.uk ↗</a></p>

Canonical is offering Ubuntu Pro users [early access to AI-generated security patches](https://ecommerce-api.datafortress.cloud/r/brieftechnews/7_wml3XBO_0HOLZj_BBQDQ/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfGNhbm9uaWNhbHMtZWRnZS1hcmNoaXZlLWFpLXdyaXR0ZW4tc2VjdXJpdHktcGF0Y2hlc3x8aHR0cHM6Ly93d3cub21ndWJ1bnR1LmNvLnVrLzIwMjYvMTEvdWJ1bnR1LXByby1haS1zZWN1cml0eS1hcmNoaXZlP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ) through a new opt-in archive called Edge. The patches are built by a multi-agent system called Surge for backporting userspace fixes.

The Edge archive is not enabled by default. You have to manually enable it with `sudo apt install pro-edge && sudo pro-enable-edge`, with optional automatic updates. Surge is not used for kernel vulnerabilities, and stable releases remain strictly human-validated. If you're comfortable running AI-generated patches on your systems, this is a way to get fixes earlier. If you're not, the default is still human-reviewed patches.

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/ueDNKkQLRQKRw7k1oFVRVQ/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfGdpdGh1YnMtb2N0b2Jlci1hdmFpbGFiaWxpdHktcmVwb3J0fHxodHRwczovL2dpdGh1Yi5ibG9nL25ld3MtaW5zaWdodHMvY29tcGFueS1uZXdzL2dpdGh1Yi1hdmFpbGFiaWxpdHktcmVwb3J0LW9jdG9iZXItMjAyNi8_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t" target="_blank" rel="noopener noreferrer">Source: github.blog ↗</a></p>

<h2 id="planetscale-iops-control-for-postgres-restores"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/PuaeZGuzwmZwWIk2MCE45g/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfHBsYW5ldHNjYWxlLWlvcHMtY29udHJvbC1mb3ItcG9zdGdyZXMtcmVzdG9yZXN8fGh0dHBzOi8vcGxhbmV0c2NhbGUuY29tL2NoYW5nZWxvZy9wb3N0Z3Jlcy1yZXN0b3JlLXN0b3JhZ2UtaW9wcy10aHJvdWdocHV0P3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ" target="_blank" rel="noopener noreferrer">PlanetScale: IOPS control for Postgres restores</a></h2>

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/PuaeZGuzwmZwWIk2MCE45g/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfHBsYW5ldHNjYWxlLWlvcHMtY29udHJvbC1mb3ItcG9zdGdyZXMtcmVzdG9yZXN8fGh0dHBzOi8vcGxhbmV0c2NhbGUuY29tL2NoYW5nZWxvZy9wb3N0Z3Jlcy1yZXN0b3JlLXN0b3JhZ2UtaW9wcy10aHJvdWdocHV0P3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ" target="_blank" rel="noopener noreferrer">Source: planetscale.com ↗</a></p>

PlanetScale now lets users [set storage IOPS and throughput when restoring Postgres backups](https://ecommerce-api.datafortress.cloud/r/brieftechnews/PuaeZGuzwmZwWIk2MCE45g/djF8d2VifDIwMjYtMTEtMTgtZGV2b3BzfHBsYW5ldHNjYWxlLWlvcHMtY29udHJvbC1mb3ItcG9zdGdyZXMtcmVzdG9yZXN8fGh0dHBzOi8vcGxhbmV0c2NhbGUuY29tL2NoYW5nZWxvZy9wb3N0Z3Jlcy1yZXN0b3JlLXN0b3JhZ2UtaW9wcy10aHJvdWdocHV0P3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ). Large restores are often limited by disk throughput, and this gives you control over that bottleneck.

The settings are available in the Restore to new branch dialog for branches on AWS network-attached storage. CLI users get `--storage-iops` and `--storage-throughput`; API users get `storage_iops` and `storage_throughput_mibs`. The settings persist on the restored branch and can be changed later. If you've ever waited hours for a big Postgres restore, this is a quality-of-life improvement worth knowing about.
