Today's biggest story is a Java vulnerability with a CVSS score that should make every platform team drop what they're doing. CVE-2026-114938, nicknamed "Java4Shell," is a critical remote code execution bug in OpenJDK's optimized AVX-512 Base64 decoding assembly. It's rated 9.2 on the CVSSv4.0 scale, it's exploitable pre-auth, and proof-of-concept exploits are already demonstrated against Jenkins, Confluence, and Tomcat. The bug is an integer underflow in hand-written assembly that leads to an out-of-bounds heap write - the kind of memory corruption that makes WAF rules useless because the payload looks like legitimate Base64.

The trigger is deceptively simple: 64 'A' characters followed by an '=' sign. That input causes an integer underflow in the AVX-512 decoding path, which then writes out of bounds on the heap. Remote unauthenticated attackers can corrupt memory and achieve code execution. The affected versions are OpenJDK 17.0.6 and later on x86-64 hardware. If you're running any Java service on modern Intel or AMD chips, you need to patch now. Don't assume your WAF will save you - the [Wiz analysis](https://ecommerce-api.datafortress.cloud/r/brieftechnews/t8TnGVwwi7vMUS2yjOogMQ/djF8d2VifDIwMjYtMTEtMjAtZGV2b3BzfHx8aHR0cHM6Ly93d3cud2l6LmlvL2Jsb2cvY3ZlLTIwMjYtMTE0OTM4LXJjZS1qYXZhNHNoZWxsLW9wZW5qZGs_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t) explicitly notes that WAF rules may not cover all exploitation paths. If you can't patch immediately, disabling Base64 intrinsics is the stopgap.

[AWS announced mutual TLS support for Network Load Balancer](https://ecommerce-api.datafortress.cloud/r/brieftechnews/-AgLbYKcQD2iaLPUSoHTIw/djF8d2VifDIwMjYtMTEtMjAtZGV2b3BzfGF3cy1ubGItZmluYWxseS1zcGVha3MtbXRsc3x8aHR0cHM6Ly9hd3MuYW1hem9uLmNvbS9ibG9ncy9uZXR3b3JraW5nLWFuZC1jb250ZW50LWRlbGl2ZXJ5L2ludHJvZHVjaW5nLW10bHMtZm9yLW5ldHdvcmstbG9hZC1iYWxhbmNlci8_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t), and it's a bigger deal than the announcement suggests. NLB operates at Layer 4 and handles millions of requests per second, but until now, anyone needing client certificate authentication had to build a home-grown mTLS solution or sit behind a third-party proxy. That meant running extra infrastructure just to terminate TLS at a layer where you shouldn't need application logic.

The new "verify mode" lets NLB authenticate client X.509 certificates, check revocation, and filter clients by certificate identity directly at the load balancer. You configure a trust store, set revocation checks, and define certificate identity filters - then the backend services never see a request from an unauthenticated client. This simplifies PKI integration and removes a whole class of home-grown proxy infrastructure. For teams running zero-trust architectures where every client must present a valid certificate, this eliminates a significant operational burden.

[OpenVINO](https://ecommerce-api.datafortress.cloud/r/brieftechnews/oHQ9DXK4mQcW20wXaKcDhw/djF8d2VifDIwMjYtMTEtMjAtZGV2b3BzfG9wZW52aW5vLWluZmVyZW5jZS1vcHRpbWl6YXRpb24td2l0aG91dC10aGUtZnJhbWV3b3JrLWxvY2staW58fGh0dHBzOi8vZ2l0aHViLmNvbS9vcGVudmlub3Rvb2xraXQvb3BlbnZpbm8_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t) is Intel's open-source toolkit for optimizing and deploying deep learning models across CPU (x86, ARM), GPU (Intel integrated and discrete), and Intel NPU accelerators. For engineers running inference in production, the appeal is resource reduction. You can take a model trained in PyTorch, convert it to OpenVINO's Intermediate Representation, and often get significant performance improvements without rewriting your training code. It's particularly useful for edge-to-cloud deployments where you need the same model running on diverse hardware. The trade-off is that you're adding a conversion step and a new runtime dependency, so it's worth benchmarking before committing.

[Together AI's post about deleting its megakernels](https://ecommerce-api.datafortress.cloud/r/brieftechnews/Xq39uHBNA-H6TUSHa8j3RQ/djF8d2VifDIwMjYtMTEtMjAtZGV2b3BzfHRoZS1tZWdha2VybmVsLWNvbWViYWNrLXN0b3J5fHxodHRwczovL3d3dy50b2dldGhlci5haS9ibG9nL3JvYWQtdG8tdG9nZXRoZXItY29tcGlsZXI_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t) is a lesson in engineering humility. Last year they built single fused GPU kernels for an entire model forward pass. This year they deleted them. The discovery: using CUDA Graphs and PDL on top of default Torch Inductor kernels recovered 98% of megakernel performance without writing any custom kernels. Then, with "multi-kernels" and agent loops, they beat their old megakernels by up to 1.7x, achieving over 1100 TPS for Llama 1B on H100.

The lesson isn't that custom kernels are bad - it's that hand-written assembly is a maintenance burden that often isn't worth the marginal gain. The default Inductor kernels plus CUDA Graphs got them 98% of the way there. The last 2% wasn't worth the complexity. This led to Together Compiler, a framework for continual AI inference optimization. If you're writing custom CUDA kernels for inference, benchmark against the defaults before you commit to that path.

[Brooker's post on workload mix](https://ecommerce-api.datafortress.cloud/r/brieftechnews/OWwMzdlb7gKN-E4Mn9xEtw/djF8d2VifDIwMjYtMTEtMjAtZGV2b3BzfHRyYWZmaWMtbWl4LXRoZS1sb2FkLXRlc3QtdmFyaWFibGUtZXZlcnlvbmUtaWdub3Jlc3x8aHR0cHM6Ly9icm9va2VyLmNvLnphL2Jsb2cvMjAyNi8xMS8xOC93b3JrbG9hZC1taXguaHRtbD91dG1fc291cmNlPWJyaWVmLXRlY2gtbmV3cy5jb20) is short but important. Microsoft's preliminary report on last week's M365 outage blames a failure to detect the issue on the specific traffic mix and SKUs used in testing labs. Using a simulator, Brooker shows that a skewed (Zipf) key distribution can either decrease throughput in a lock-contention model or increase it in a cache model, depending on the system. Throughput can vary by multiple orders of magnitude depending on key skew.

The lesson: load tests must accurately reflect production traffic patterns to be meaningful. If your production workload has hot keys and your load test uses uniform distribution, your results are fiction. This is the kind of thing that causes outages that "came out of nowhere" - the system was fine in testing because the testing didn't look like production.

[GitHub CLI v2.105.0 adds Event Streams support](https://ecommerce-api.datafortress.cloud/r/brieftechnews/VfwF3MicZwU1Kj-jp1gxxA/djF8d2VifDIwMjYtMTEtMjAtZGV2b3BzfGdpdGh1Yi1jbGktc3RvcHMtcG9sbGluZ3x8aHR0cHM6Ly9naXRodWIuYmxvZy9jaGFuZ2Vsb2cvMjAyNi0xMS0xOC13YWl0LWZvci1wdWxsLXJlcXVlc3QtZXZlbnRzLXdpdGgtZ2l0aHViLWNsaS8_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t), letting scripts wait for pull request events with a single command. The `gh event listen` command creates a subscription and prints each event as JSON, exiting after the first event by default. Options include `--count`, `--follow`, and `--timeout`. You can wait for submitted reviews, state changes, merge conflicts, and completed check suites.

This replaces the polling pattern that every CI script has - check for a review, sleep, check again. It's in preview and requires access to the Event Streams waitlist, but it's the right direction. For anyone writing automation around PR workflows, this eliminates a whole category of race conditions and wasted API calls.
