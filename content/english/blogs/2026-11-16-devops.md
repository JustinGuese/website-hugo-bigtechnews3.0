[Solo.io's kagent 1.0](https://ecommerce-api.datafortress.cloud/r/brieftechnews/lFlRGSYeu7nG3-vmXTVMcQ/djF8d2VifDIwMjYtMTEtMTYtZGV2b3BzfGthZ2VudC0xMC1nYS1hZ2VudHMtYXMtYWN0b3JzLW5vdC1wb2RzfHxodHRwczovL3d3dy5zb2xvLmlvL2Jsb2cvYW5ub3VuY2luZy1rYWdlbnQtMS0wLWdhP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ) is the enterprise distribution of Agent Substrate, which just became a CNCF project. The core idea: treat each agent as an actor with a sandbox, state, and durable identity, then schedule those actors onto warm worker Pods. Idle actors get suspended to free compute and restored on the next request.

This directly attacks the pod-per-agent failure mode. Long-running agent harnesses and tool sandboxes do not map cleanly to a single Pod lifecycle, and the churn of spinning Pods up and down for every agent interaction wastes scheduling overhead and leaves state management to the application. kagent layers user, conversation, and agent management on top of the actor substrate. It is already in production at scale with customers, and works on any Kubernetes distribution including OpenShift. For teams running agents in production, this is the first serious alternative to treating every agent invocation like a microservice call.

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/8qgT4XZILf1eqGXrFBI_dA/djF8d2VifDIwMjYtMTEtMTYtZGV2b3BzfGZseWlvLXRocm93cy1vdXQtdGhlLXBob25lYm9va3x8aHR0cHM6Ly9mbHkuaW8vYmxvZy90aHJvd2luZy1vdXQtdGhlLXBob25lYm9vay8_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t" target="_blank" rel="noopener noreferrer">Source: fly.io ↗</a></p>

[Fly.io rebuilt its 6PN private network](https://ecommerce-api.datafortress.cloud/r/brieftechnews/8qgT4XZILf1eqGXrFBI_dA/djF8d2VifDIwMjYtMTEtMTYtZGV2b3BzfGZseWlvLXRocm93cy1vdXQtdGhlLXBob25lYm9va3x8aHR0cHM6Ly9mbHkuaW8vYmxvZy90aHJvd2luZy1vdXQtdGhlLXBob25lYm9vay8_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t) by deleting the thing that made it scale poorly: a synchronized map of every Machine's location kept on every host. The old design meant hundreds of thousands of routing entries per host, all needing to stay consistent. The new one encodes routing information directly into the address - netid, hostid, mach - and uses an eBPF program (udp-xdp) to shuffle bytes so packets match kernel routes without a lookup.

The result is 100 to 200 records per host instead of hundreds of thousands, with no lookups, no state, and no database to synchronize. The cost: Machine migrations between hosts need special handling, since the address now encodes location. But this is the right trade for a network where most traffic is between a small set of Machines, and it kills an entire class of cache-invalidation and consistency problems that plague large distributed systems.

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/z6Oq3G4M_FvLjsOycwtUhQ/djF8d2VifDIwMjYtMTEtMTYtZGV2b3BzfGdhbmctc2NoZWR1bGluZy1hbmQtdG9wb2xvZ3ktYXdhcmUtcGxhY2VtZW50LWZvci1haS10cmFpbmluZ3x8aHR0cHM6Ly93d3cuY25jZi5pby9ibG9nLzIwMjYvMTEvMTIvZ2FuZy1zY2hlZHVsaW5nLWFuZC10b3BvbG9neS1hd2FyZS1wbGFjZW1lbnQtZm9yLWFpLXRyYWluaW5nLWluLWt1YmVybmV0ZXMvP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ" target="_blank" rel="noopener noreferrer">Source: cncf.io ↗</a></p>

Kubernetes' built-in scheduler is fine for web backends and terrible for distributed AI training. It schedules pods individually, which means a distributed job can start with half its pods running and half queued, leaving GPUs idle and burning money. And it has no notion of inter-GPU bandwidth, so pods can land on hardware where the training traffic crawls.

The [CNCF walkthrough](https://ecommerce-api.datafortress.cloud/r/brieftechnews/z6Oq3G4M_FvLjsOycwtUhQ/djF8d2VifDIwMjYtMTEtMTYtZGV2b3BzfGdhbmctc2NoZWR1bGluZy1hbmQtdG9wb2xvZ3ktYXdhcmUtcGxhY2VtZW50LWZvci1haS10cmFpbmluZ3x8aHR0cHM6Ly93d3cuY25jZi5pby9ibG9nLzIwMjYvMTEvMTIvZ2FuZy1zY2hlZHVsaW5nLWFuZC10b3BvbG9neS1hd2FyZS1wbGFjZW1lbnQtZm9yLWFpLXRyYWluaW5nLWluLWt1YmVybmV0ZXMvP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ) covers the two fixes: topology-aware scheduling (TAS) to place pods on hardware with appropriate inter-GPU bandwidth, and gang scheduling so all pods in a job start together. Both are implemented by Kueue and the Coscheduling plugin. If you are running GPU training on Kubernetes and have not looked at these, you are leaving a measurable fraction of your GPU spend on the table.

[Google Cloud's TPU Sync](https://ecommerce-api.datafortress.cloud/r/brieftechnews/Nojpx3pQMJAFot8KgbKNKg/djF8d2VifDIwMjYtMTEtMTYtZGV2b3BzfGdvb2dsZS1vcGVuLXNvdXJjZXMtdHB1LXN5bmN8fGh0dHBzOi8vd3d3LmluZm9xLmNvbS9uZXdzLzIwMjYvMTEvZ29vZ2xlLXRwdS1zeW5jLz91dG1fc291cmNlPWJyaWVmLXRlY2gtbmV3cy5jb20) is a native C++ library that moves KV cache blocks and model weights between TPU HBM, host DRAM, shared storage, and the data center network. It targets long-context and disaggregated LLM serving plus RL loops, where data movement is often the real bottleneck.

The numbers are the story. Median KV transfer latency for Qwen3 235B dropped from several seconds to about 230 ms. It ships Python wheels for JAX and PyTorch, with APIs for the KV cache manager, KV store, and weight synchronizer, and integrates with vLLM-TorchTPU and SGLang-TorchTPU. Validated on TPU v7x and v6e. If you are serving long-context models on TPUs, this is the missing piece.

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/_CephzHpl8Uh0wiRPZX8lA/djF8d2VifDIwMjYtMTEtMTYtZGV2b3BzfGFwYWNoZS1tb2RodHRwMi1wYXRjaC1ub3ctaXQtaXMtdW5hdXRoZW50aWNhdGVkfHxodHRwczovL3dlYmZsb3cuc3lzZGlnLmNvbS9ibG9nL2h0dHBkLWN2ZS0yMDI2LTExOTYxOC1kZXRlY3RpbmctaGVhcC1jb3JydXB0aW9uLWFuZC1yY2UtaW4tYXBhY2hlLWh0dHAtc2VydmVyLW1vZC1odHRwMj91dG1fc291cmNlPWJyaWVmLXRlY2gtbmV3cy5jb20" target="_blank" rel="noopener noreferrer">Source: webflow.sysdig.com ↗</a></p>

[CVE-2026-119618](https://ecommerce-api.datafortress.cloud/r/brieftechnews/_CephzHpl8Uh0wiRPZX8lA/djF8d2VifDIwMjYtMTEtMTYtZGV2b3BzfGFwYWNoZS1tb2RodHRwMi1wYXRjaC1ub3ctaXQtaXMtdW5hdXRoZW50aWNhdGVkfHxodHRwczovL3dlYmZsb3cuc3lzZGlnLmNvbS9ibG9nL2h0dHBkLWN2ZS0yMDI2LTExOTYxOC1kZXRlY3RpbmctaGVhcC1jb3JydXB0aW9uLWFuZC1yY2UtaW4tYXBhY2hlLWh0dHAtc2VydmVyLW1vZC1odHRwMj91dG1fc291cmNlPWJyaWVmLXRlY2gtbmV3cy5jb20) is a critical heap corruption bug in Apache HTTP Server's mod_http2, fixed in 2.4.71. It affects versions 2.4.55 through 2.4.70, lives in assign_headers(), and triggers over HTTP/2 with no authentication. Red Hat and Amazon score it 9.8 on CVSS v3.1; CISA says 8.1.

It was found independently by Anthropic's OSS Scanner and Google Cloud Vulnerability Research. A public PoC for heap corruption exists, but no RCE PoC or in-the-wild exploitation has been confirmed. Only servers with HTTP/2 enabled are exposed - which is most of them. Upgrade to 2.4.71 or disable HTTP/2 while you patch.

[Meta won the CNCF End User Case Study Contest](https://ecommerce-api.datafortress.cloud/r/brieftechnews/MNvVow9JZ-DlwzlxkTccvw/djF8d2VifDIwMjYtMTEtMTYtZGV2b3BzfG1ldGFzLWdpdG9wcy13aW4tZ29vZ2xlcy1hZ2VudGljLXBvbGljeS1hbmQtZ3JhY2VmdWwtYWktZGVncmFkYXRpb258fGh0dHBzOi8vd3d3LmNuY2YuaW8vYW5ub3VuY2VtZW50cy8yMDI2LzExLzExL21ldGEtd2lucy1jbmNmLWVuZC11c2VyLWNhc2Utc3R1ZHktY29udGVzdC1mb3ItYWNjZWxlcmF0aW5nLWFpLWluZnJhc3RydWN0dXJlLWRlcGxveW1lbnRzLWZyb20taG91cnMtdG8tbWludXRlcy8_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t) for a GitOps platform built on Argo CD and Kargo across roughly 100 Kubernetes clusters supporting AI research and inference. Routine application deployments went from over four hours to minutes, using a simplified application definition with automated deployment configuration, independent release promotion, and health verification. They separated application delivery from infrastructure provisioning, keeping Terraform for the latter.

[Google Cloud made its Organization Policy MCP server generally available](https://ecommerce-api.datafortress.cloud/r/brieftechnews/kvsrJrkBfr7zwA2Voxhz-Q/djF8d2VifDIwMjYtMTEtMTYtZGV2b3BzfG1ldGFzLWdpdG9wcy13aW4tZ29vZ2xlcy1hZ2VudGljLXBvbGljeS1hbmQtZ3JhY2VmdWwtYWktZGVncmFkYXRpb258fGh0dHBzOi8vY2xvdWQuZ29vZ2xlLmNvbS9ibG9nL3Byb2R1Y3RzL2lkZW50aXR5LXNlY3VyaXR5L2FpLXBvd2VyZWQtY2xvdWQtZ292ZXJuYW5jZS13aGF0cy1uZXctaW4tb3JnYW5pemF0aW9uLXBvbGljeS8_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t) and added Gemini-powered natural-language authoring of custom constraints. The MCP server lets agents and pipelines audit posture, detect drift, and manage exemptions through tools like ListConstraints and GetEffectivePolicy, over a catalog of 100+ predefined policies. Agentic governance is here whether you asked for it or not.

Finally, [incident.io's piece on graceful degradation](https://ecommerce-api.datafortress.cloud/r/brieftechnews/hXD79gQ3b5OF46GkfBXMfQ/djF8d2VifDIwMjYtMTEtMTYtZGV2b3BzfG1ldGFzLWdpdG9wcy13aW4tZ29vZ2xlcy1hZ2VudGljLXBvbGljeS1hbmQtZ3JhY2VmdWwtYWktZGVncmFkYXRpb258fGh0dHBzOi8vaW5jaWRlbnQuaW8vYmxvZy9kZWdyYWRlLWdyYWNlZnVsbHktZGVzaWduaW5nLWFpLWZlYXR1cmVzLXRoYXQta2VlcC13b3JraW5nLXdoZW4tdGhlLW1vZGVsLWRvZXNudD91dG1fc291cmNlPWJyaWVmLXRlY2gtbmV3cy5jb20) makes the case that when an AI feature fails, the fallback model is not the answer. Skyscanner's Michael Tweed and incident.io's Sahaj Sawhney both chose graceful degradation over better fallback models, because failing over to another model means losing not just the output but the understanding built up by doing the work manually. As AI becomes a critical dependency, planning for the model being wrong or down is the resilience work that matters.
