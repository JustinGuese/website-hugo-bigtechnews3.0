[The shared-versus-dedicated Kubernetes cluster debate](https://ecommerce-api.datafortress.cloud/r/brieftechnews/3AfmOmpwS7m7Gv-C8PFZdQ/djF8d2VifDIwMjYtMTEtMjctZGV2b3BzfGRlZGljYXRlZC1jbHVzdGVycy13aGVuLXNoYXJlZC1pbmZyYXN0cnVjdHVyZS1zdG9wcy1wYXlpbmd8fGh0dHBzOi8vY2xvdWRuYXRpdmVub3cuY29tL2NvbnRyaWJ1dGVkLWNvbnRlbnQvZGVkaWNhdGVkLWNsdXN0ZXJzLXBlci13b3JrbG9hZC13aGVuLXNoYXJlZC1zdG9wcy1wYXlpbmcvP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ) usually devolves into vibes. This piece, drawing on experience at a streaming platform and Lucid Motors, gives you actual criteria. Blast radius is the big one - if one noisy neighbor can take down your critical workload, shared stops being a cost optimization and becomes a liability.

The authors flag four triggers: blast radius, network reach exceptions, singleton job risks, and divergent lifecycles. The costs of going dedicated are real and often underestimated - duplicated platform components, multiplied upgrade work, policy drift, and a larger on-call surface. The decision isn't about performance, it's about boundaries and risk. If you can't articulate which of those four triggers applies to your workload, you're probably fine staying shared.

The lesson for anyone running CI: environmental misconfigurations and insufficient memory cause multi-stage failures far more often than code bugs. If you're debugging a pipeline failure, skip the error banner and go straight to the detailed logs. And if multiple stages fail simultaneously, check disk space and memory before you start reading code.

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/5dEvaNqb0444szFcXyd4Ag/djF8d2VifDIwMjYtMTEtMjctZGV2b3BzfGRvbnQtZ2l2ZS10aGUtcm9ib3QteW91ci1zc2gta2V5c3x8aHR0cHM6Ly90aGVuZXdzdGFjay5pby90ZWxlcG9ydC1hZ2VudC1kZWxlZ2F0ZWQtaWRlbnRpdHkvP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ" target="_blank" rel="noopener noreferrer">Source: thenewstack.io ↗</a></p>

[Teleport field CTO Boris Kurktchiev makes the case](https://ecommerce-api.datafortress.cloud/r/brieftechnews/5dEvaNqb0444szFcXyd4Ag/djF8d2VifDIwMjYtMTEtMjctZGV2b3BzfGRvbnQtZ2l2ZS10aGUtcm9ib3QteW91ci1zc2gta2V5c3x8aHR0cHM6Ly90aGVuZXdzdGFjay5pby90ZWxlcG9ydC1hZ2VudC1kZWxlZ2F0ZWQtaWRlbnRpdHkvP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ) for delegated identity in AI agents. Agents start with zero access, request only what a task needs, and every action links back to the person who assigned the work. No more handing an agent your production SSH keys and hoping it doesn't do something creative.

Teleport announced Beams at KubeCon, an agent runtime combining sandboxing, identity, access, observability, and auditing. But Kurktchiev's point stands: "just having a sandbox is not enough" - you still need to control what the sandbox can reach. The policy-based model across people, workloads, and agents is the right framing for anyone who's been asked to "just give the AI access" by an enthusiastic VP.

<h2 id="the-data-center-shapes-the-ai-workload"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/bO7QFuT0oFtX37xwruizVQ/djF8d2VifDIwMjYtMTEtMjctZGV2b3BzfHRoZS1kYXRhLWNlbnRlci1zaGFwZXMtdGhlLWFpLXdvcmtsb2FkfHxodHRwczovL3d3dy5uc2NhbGUuY29tL2Jsb2cvaG93LXRoZS1kYXRhLWNlbnRlci1zaGFwZXMtdGhlLWFpLXdvcmtsb2FkP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ" target="_blank" rel="noopener noreferrer">The Data Center Shapes the AI Workload</a></h2>

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/bO7QFuT0oFtX37xwruizVQ/djF8d2VifDIwMjYtMTEtMjctZGV2b3BzfHRoZS1kYXRhLWNlbnRlci1zaGFwZXMtdGhlLWFpLXdvcmtsb2FkfHxodHRwczovL3d3dy5uc2NhbGUuY29tL2Jsb2cvaG93LXRoZS1kYXRhLWNlbnRlci1zaGFwZXMtdGhlLWFpLXdvcmtsb2FkP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ" target="_blank" rel="noopener noreferrer">Source: nscale.com ↗</a></p>

[Nscale's engineering overview](https://ecommerce-api.datafortress.cloud/r/brieftechnews/bO7QFuT0oFtX37xwruizVQ/djF8d2VifDIwMjYtMTEtMjctZGV2b3BzfHRoZS1kYXRhLWNlbnRlci1zaGFwZXMtdGhlLWFpLXdvcmtsb2FkfHxodHRwczovL3d3dy5uc2NhbGUuY29tL2Jsb2cvaG93LXRoZS1kYXRhLWNlbnRlci1zaGFwZXMtdGhlLWFpLXdvcmtsb2FkP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ) connects data center topology to GPU cluster performance. The key insight: cluster traffic runs on multiple networks - front-end Ethernet for SSH, TCP handshakes, and storage, plus a back-end network for RDMA. Where you put CPU nodes matters: colocate them with GPUs for hot-path workloads like agentic RL loops, but keep them separate for pre-tokenization.

Larger NVLink domains change where communication-heavy parallelism can run, and SHARP does collective aggregation inside switches. Once a job spans more than one node, these decisions directly impact latency. If you're provisioning GPU clusters, the network fabric is not an afterthought - it's half the performance story.
