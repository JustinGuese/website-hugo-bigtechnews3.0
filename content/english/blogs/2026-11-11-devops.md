Google's [GKE dynamic slicing is now generally available for TPUs](https://ecommerce-api.datafortress.cloud/r/brieftechnews/92wfEnDbALCBhQVNJkIY0w/djF8d2VifDIwMjYtMTEtMTEtZGV2b3BzfGdrZS1keW5hbWljLXNsaWNpbmctaXMtZ2EtYW5kLWl0cy1mYXN0fHxodHRwczovL2Nsb3VkLmdvb2dsZS5jb20vYmxvZy9wcm9kdWN0cy9jb250YWluZXJzLWt1YmVybmV0ZXMvZ2tlLWR5bmFtaWMtc2xpY2luZy1vbi10cHVzLz91dG1fc291cmNlPWJyaWVmLXRlY2gtbmV3cy5jb20). The change: slice formation is now decoupled from nodepool provisioning. Previously, if you wanted a TPU slice, you had to provision the entire nodepool first, then wait for the slice to form. That's two sequential waits. Now they happen in parallel, which is why startup times drop by up to 5x and recovery by 4.5x.

For anyone running large model training on GKE, this is the difference between a failed TPU node killing an afternoon and it costing you a coffee break. The feature also means you can resize slices without ripping up the nodepool, which is the kind of operational flexibility that makes TPU fleets actually manageable. If you've been holding off on TPUs because of the operational pain, this removes a real chunk of it.

[AWS announced Nitro Sandboxes for Amazon EKS](https://ecommerce-api.datafortress.cloud/r/brieftechnews/KI3TTmhkNr809GaTauWi7w/djF8d2VifDIwMjYtMTEtMTEtZGV2b3BzfGF3cy1uaXRyby1zYW5kYm94ZXMtaGFyZHdhcmUtaXNvbGF0aW9uLWZvci1ldmVyeS1wb2R8fGh0dHBzOi8vYXdzLmFtYXpvbi5jb20vYmxvZ3MvY29udGFpbmVycy9hd3Mtbml0cm8tc2FuZGJveGVzLWhhcmR3YXJlLWVuZm9yY2VkLXdvcmtsb2FkLWlzb2xhdGlvbi1vbi1hbWF6b24tZWtzLz91dG1fc291cmNlPWJyaWVmLXRlY2gtbmV3cy5jb20), giving each pod its own lightweight VM backed by the Nitro System. The pitch: the isolation of a dedicated EC2 instance with the simplicity of a Kubernetes pod. Enable it with a single line in the pod spec - no container image changes, no pipeline rewrites.

There are two modes. Isolated mode gives standard hardware-enforced protection. Confidential mode adds cryptographic attestation, which is what regulated workloads and multi-tenant SaaS need. This is aimed squarely at the shared-kernel problem: AI agents, untrusted LLM-generated code, and any workload where a kernel escape would be catastrophic. The cost angle is real too - you no longer need a dedicated instance per sensitive workload, so you can consolidate while getting stronger isolation. Near bare-metal performance, per AWS.

[This piece from Cloud Native Now](https://ecommerce-api.datafortress.cloud/r/brieftechnews/eMmnj6meHNMezEC2Q5P37g/djF8d2VifDIwMjYtMTEtMTEtZGV2b3BzfGt1YmVybmV0ZXMtcmVzdGFydHMtYWktYWdlbnRzLWJ1dC1jYW50LXJlY292ZXItdGhlaXItd29ya3x8aHR0cHM6Ly9jbG91ZG5hdGl2ZW5vdy5jb20vY29udHJpYnV0ZWQtY29udGVudC9rdWJlcm5ldGVzLWdhdmUtYWktYWdlbnRzLWEtcGxhY2UtdG8tcnVuLWJ1dC1ub3QtYS13YXktdG8tcmVjb3Zlci8_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t) nails the gap: Kubernetes can restore an agent's environment, but it has no record of which steps completed. A restarted agent will happily re-run a payment it already made. That's not a hypothetical - that's the failure mode that makes production agents dangerous.

Two projects are trying to fix this. Kubernetes SIG Apps' Agent Sandbox gives stateful pods with stable identity. Google's Agent Substrate isolates agents in microVMs or gVisor and resumes them in under 500ms. But neither tracks completed execution steps. The author argues for durable execution that logs each step, pointing at Dapr's workflow engine as an option. Until Kubernetes gets execution history baked in, agents need both sandboxing and a durable execution record, or they're not safe to let loose with credentials.

[CloudNativePG became a CNCF incubating project](https://ecommerce-api.datafortress.cloud/r/brieftechnews/dJiaTQj_4qa5ofIVDxl0yw/djF8d2VifDIwMjYtMTEtMTEtZGV2b3BzfGNsb3VkbmF0aXZlcGctaGl0cy1jbmNmLWluY3ViYXRpb258fGh0dHBzOi8vd3d3LmNuY2YuaW8vYmxvZy8yMDI2LzExLzEwL2Nsb3VkbmF0aXZlcGctYmVjb21lcy1hLWNuY2YtaW5jdWJhdGluZy1wcm9qZWN0Lz91dG1fc291cmNlPWJyaWVmLXRlY2gtbmV3cy5jb20), up from Sandbox.
