Autonome KI-Schleifen haben bei Anthropic etablierte Entwicklerwerkzeuge überlastet. Das Unternehmen gab bekannt, [Git aufgegeben und ein eigenes VCS](https://ecommerce-api.datafortress.cloud/r/brieftechnews/SZTQ8re6M-J4TfSmNiGfxQ/djF8d2VifDIwMjYtMTAtMTUtaXR8YW50aHJvcGljLWVyc2V0enQtZ2l0LWR1cmNoLXNjaW9uLW5hY2gtMzAwMDAta2ktbWVyZ2VzLXByby10YWd8fGh0dHBzOi8vd3d3LmFudGhyb3BpYy5jb20vZW5naW5lZXJpbmcvcmVkZXNpZ25pbmctc291cmNlLWNvbnRyb2w_dXRtX3NvdXJjZT1icmllZi10ZWNoLW5ld3MuY29t) namens Scion für das interne Engineering-Monorepo entwickelt zu haben. Das System senkte CI-Checkout-Zeiten von mehreren Minuten auf wenige Sekunden und reduzierte den Speicher- sowie CPU-Bedarf der Entwicklerinfrastruktur um den Faktor 200.

<h2 id="behebung-von-32-ms-tail-latency-bei-inaktiven-clickhouse-verbindungen"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/95tw_QJcUboviSlR9Tuw4g/djF8d2VifDIwMjYtMTAtMTUtaXR8YmVoZWJ1bmctdm9uLTMyLW1zLXRhaWwtbGF0ZW5jeS1iZWktaW5ha3RpdmVuLWNsaWNraG91c2UtdmVyYmluZHVuZ2VufHxodHRwczovL2NsaWNraG91c2UuY29tL2Jsb2cvY2hhc2luZy0zMm1zLXRhaWwtbGF0ZW5jeS1jbGlja2hvdXNlP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ" target="_blank" rel="noopener noreferrer">Behebung von 32 ms Tail-Latency bei inaktiven ClickHouse-Verbindungen</a></h2>

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/95tw_QJcUboviSlR9Tuw4g/djF8d2VifDIwMjYtMTAtMTUtaXR8YmVoZWJ1bmctdm9uLTMyLW1zLXRhaWwtbGF0ZW5jeS1iZWktaW5ha3RpdmVuLWNsaWNraG91c2UtdmVyYmluZHVuZ2VufHxodHRwczovL2NsaWNraG91c2UuY29tL2Jsb2cvY2hhc2luZy0zMm1zLXRhaWwtbGF0ZW5jeS1jbGlja2hvdXNlP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ" target="_blank" rel="noopener noreferrer">Source: clickhouse.com ↗</a></p>

ClickHouse analysierte einen Edge-Case, bei dem native TCP-`SELECT`-Abfragen über Verbindungen mit höherer Latenz [ihre Roundtrip-Zeit verdoppelten](https://ecommerce-api.datafortress.cloud/r/brieftechnews/95tw_QJcUboviSlR9Tuw4g/djF8d2VifDIwMjYtMTAtMTUtaXR8YmVoZWJ1bmctdm9uLTMyLW1zLXRhaWwtbGF0ZW5jeS1iZWktaW5ha3RpdmVuLWNsaWNraG91c2UtdmVyYmluZHVuZ2VufHxodHRwczovL2NsaWNraG91c2UuY29tL2Jsb2cvY2hhc2luZy0zMm1zLXRhaWwtbGF0ZW5jeS1jbGlja2hvdXNlP3V0bV9zb3VyY2U9YnJpZWYtdGVjaC1uZXdzLmNvbQ) - von rund 32 ms auf rund 64 ms nach einer Leerlaufphase.

Die Ursache lag im Zusammenspiel zwischen dem OS-TCP-Stack und dem Framing des Datenbankprotokolls. In Phasen ohne Datenverkehr setzt der Kernel das TCP Congestion Window (`cwnd`) auf die Initialgröße zurück. Führte der Client eine Abfrage aus, sendete das native ClickHouse-Protokoll die Ergebnisdaten gefolgt von einer Reihe ungebündelter Metadaten-Frames (`ProfileEvents`, `Progress`, `Logs`) und einem `EndOfStream`-Paket. Selbst bei gesetztem `TCP_NODELAY` überstieg diese Häufung kleiner Metadatenpakete das verkleinerte `cwnd`. Die Verbindung blockierte und musste einen vollen RTT auf ein ACK warten, bevor die letzten Bytes übertragen werden konnten. ClickHouse behob die Verzögerung, indem Metadatenpakete nun auf Anwendungsebene gebündelt an das Socket übergeben werden.

```
Idle Connection -> cwnd resets to initial window (e.g., 10 segments)
Query Response  -> Data + Unbatched Metadata (Progress, Logs, EndOfStream)
Result          -> Exceeds cwnd -> Stalls pipeline -> +1 RTT (32 ms penalty)
Fix             -> Application-layer frame batching -> Fits within initial cwnd
```
