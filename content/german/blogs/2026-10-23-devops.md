PlanetScale beschrieb in [I Don't Trust ON DELETE CASCADE](https://ecommerce-api.datafortress.cloud/r/brieftechnews/OELQt-zjW-D18IC0qVHeVQ/djF8d2VifDIwMjYtMTAtMjMtZGV2b3BzfHdhcnVtLW9uLWRlbGV0ZS1jYXNjYWRlLWRpZS12ZXJmw7xnYmFya2VpdC12b24tZGF0ZW5iYW5rZW4tZ2Vmw6RocmRldHx8aHR0cHM6Ly9wbGFuZXRzY2FsZS5jb20vYmxvZy9pLWRvbnQtbGlrZS1kZWxldGUtY2FzY2FkZT91dG1fc291cmNlPWJyaWVmLXRlY2gtbmV3cy5jb20) ein klassisches Problem relationaler Datenbanken. Kaskadierende Löschvorgänge vereinfachen zwar die Anwendungslogik, indem sie untergeordnete Datensätze automatisch entfernen, führen bei großen Datenmengen jedoch zu unberechenbarem Sperrverhalten.

Das Kernproblem liegt in Sperrkonflikten. In PostgreSQL hält eine umfangreiche Kaskadierung über die gesamte Dauer des Vorgangs ein `RowExclusiveLock` auf mehreren verknüpften Tabellen, erzeugt massives Volumen im Write-Ahead Log (WAL) und blockiert Transaktionen. Versucht eine separate Migration in diesem Zeitfenster ein einfaches `ALTER TABLE`, fordert sie ein `AccessExclusiveLock` an und reiht sich hinter der Kaskade ein. Nachfolgende Abfragen stauen sich wiederum hinter der blockierten Migration, erschöpfen rasch die Verbindungspools und lösen einen Ausfall aus. Der Artikel empfiehlt stattdessen explizite Soft Deletes, kombiniert mit begrenzten, paketierten Bereinigungs-Jobs im Hintergrund sowie strengen `lock_timeout`-Vorgaben für Migrationen.

<h2 id="github-actions-führt-native-commit-lockfiles-ein"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/vldbN7Dv4K-dFJGZ_cMYDQ/djF8d2VifDIwMjYtMTAtMjMtZGV2b3BzfGdpdGh1Yi1hY3Rpb25zLWbDvGhydC1uYXRpdmUtY29tbWl0LWxvY2tmaWxlcy1laW58fGh0dHBzOi8vZ2l0aHViLmJsb2cvY2hhbmdlbG9nLzIwMjYtMTAtMTQtZ2l0aHViLWFjdGlvbnMtd29ya2Zsb3ctbG9ja2ZpbGVzLWluLXB1YmxpYy1wcmV2aWV3Lz91dG1fc291cmNlPWJyaWVmLXRlY2gtbmV3cy5jb20" target="_blank" rel="noopener noreferrer">GitHub Actions führt native Commit-Lockfiles ein</a></h2>

<p class="small mb-4"><a href="https://ecommerce-api.datafortress.cloud/r/brieftechnews/vldbN7Dv4K-dFJGZ_cMYDQ/djF8d2VifDIwMjYtMTAtMjMtZGV2b3BzfGdpdGh1Yi1hY3Rpb25zLWbDvGhydC1uYXRpdmUtY29tbWl0LWxvY2tmaWxlcy1laW58fGh0dHBzOi8vZ2l0aHViLmJsb2cvY2hhbmdlbG9nLzIwMjYtMTAtMTQtZ2l0aHViLWFjdGlvbnMtd29ya2Zsb3ctbG9ja2ZpbGVzLWluLXB1YmxpYy1wcmV2aWV3Lz91dG1fc291cmNlPWJyaWVmLXRlY2gtbmV3cy5jb20" target="_blank" rel="noopener noreferrer">Source: github.blog ↗</a></p>

GitHub hat [Workflow Lockfiles in die Public Preview](https://ecommerce-api.datafortress.cloud/r/brieftechnews/vldbN7Dv4K-dFJGZ_cMYDQ/djF8d2VifDIwMjYtMTAtMjMtZGV2b3BzfGdpdGh1Yi1hY3Rpb25zLWbDvGhydC1uYXRpdmUtY29tbWl0LWxvY2tmaWxlcy1laW58fGh0dHBzOi8vZ2l0aHViLmJsb2cvY2hhbmdlbG9nLzIwMjYtMTAtMTQtZ2l0aHViLWFjdGlvbnMtd29ya2Zsb3ctbG9ja2ZpbGVzLWluLXB1YmxpYy1wcmV2aWV3Lz91dG1fc291cmNlPWJyaWVmLXRlY2gtbmV3cy5jb20) für alle Account-Klassen überführt. CI-Workflows auf veränderliche Git-Tags wie `@v4` zu verweisen, birgt erhebliche Supply-Chain-Risiken, da ein Angreifer nach einer Kompromittierung des Upstream-Repositories den Tag auf bösartigen Code umbiegen kann. Das Festschreiben auf vollständige SHA-Hashes löst das Sicherheitsproblem, macht Workflow-Dateien jedoch unleserlich und schwer wartbar.

Workflow-Lockfiles lösen diesen Konflikt. Workflows können weiterhin lesbare Tags referenzieren, während eine lokale Datei unter `.github/workflows/actions.lock` Actions und wiederverwendbare Workflows an unveränderliche Git-Commit-Hashes bindet. Plattformteams können diese Dateien über die CLI-Erweiterung `gh actions-lock` verwalten, Updates per Dependabot automatisieren und über eine unternehmensweite `Require lockfile`-Richtlinie die Ausführung nicht erfasster Actions unterbinden.

Administratoren müssen mobile und Desktop-Endpunkte umgehend auf den Cloudflare One Client v2.5.7 unter Android, v1.12.7 unter iOS sowie die entsprechenden neuen Desktop-Builds aktualisieren, um Angriffe auf die Zertifikatsvalidierung auszuschließen.
